# Design

## Context

动机与功能边界见 [proposal.md](proposal.md)，验收行为见本变更的七个 `specs/*/spec.md`。仓库目前仅有 OpenSpec 配置和技能文件，没有应用、构建系统或既有行为需要迁移。本设计满足新架构、外部依赖和并发状态管理的条件，因此需要完整设计文档。

用户已确认独立 Lore 客户端、程序员工作流、Windows x64 首发，以及 Avalonia 12、编译绑定和 NativeAOT。以下是规划采用的工程默认值：.NET 10、MVVM、解压即用的目录发行包、文件级暂存、只读差异和外部冲突编辑。它们不代表已经通过实现验证。

调研依据（访问日期：2026-10-13；链接指向上游当前分支，实施时固定实际依赖版本）：

- [SourceGit 项目](https://github.com/sourcegit-scm/sourcegit/blob/master/src/SourceGit.csproj)使用 Avalonia 11 系列；其[仓库 ViewModel](https://github.com/sourcegit-scm/sourcegit/blob/master/src/ViewModels/Repository.cs)和[命令层](https://github.com/sourcegit-scm/sourcegit/blob/master/src/Commands/Command.cs)直接依赖 Git 操作。借鉴交互而独立实现符合本项目定位。
- [Avalonia 12 迁移说明](https://docs.avaloniaui.net/docs/avalonia12-breaking-changes)推荐 .NET 10，并默认启用编译绑定；[AOT 文档](https://docs.avaloniaui.net/docs/deployment/native-aot)要求关注编译 XAML、资源和服务创建方式。
- [LoreVcs](https://github.com/EpicGames/lore-dotnet)通过独立 RID 运行包提供原生库；[示例](https://github.com/EpicGames/lore-dotnet/blob/main/examples/example/Program.cs)覆盖创建、暂存、提交、推送和克隆。[生成模板](https://github.com/EpicGames/lore-dotnet/tree/main/generator/templates)使用 P/Invoke 与工作线程事件回调，事件访问受原生内存生命周期约束。
- [Lore 状态与暂存设计](https://epicgames.github.io/lore/explanation/system-design/#15-state-detection-and-staging)将变更标记与暂存意图分开；默认状态查询不扫描磁盘，提交读取已暂存路径的当前内容。
- [AvaloniaEdit 的依赖配置](https://github.com/AvaloniaUI/AvaloniaEdit/blob/master/Directory.Packages.props)已经使用 Avalonia 12。主分支适配不等于发布包或本项目 AOT 验证通过。

## Goals / Non-Goals

**Goals:**

- 让 UI 与具体 SDK 版本隔离，使用类型化数据和事件实现可诊断的版本管理操作。
- 把 NativeAOT 发布产物作为交付依据，及早验证原生边界和文本控件。
- 由 Lore 决定仓库状态与操作结果；客户端负责清楚呈现意图、进度、冲突和恢复入口。
- 用可控的测试仓库验证真实数据行为，同时用可延迟、失败的测试适配器验证界面竞态。

**Non-Goals:**

- 不自行读写 Lore 的内部存储格式，不实现版本控制算法或远端服务器。
- 不建设多 VCS 插件框架，不复制 SourceGit 的 Git 命令层或整个 Avalonia 11 UI。
- 不把首个 AOT 验证里程碑当作整个首版已交付；完成条件仍是全部 capability 的工作流闭环。

## Decisions

### 1. 固定 Avalonia 12 与 .NET 10，持续生成 NativeAOT 产物

主应用目标为 `net10.0`、`win-x64`，启用 `PublishAot` 和显式的 `AvaloniaUseCompiledBindingsByDefault`；自有库启用 AOT 兼容性分析。视图与数据模板声明 `x:DataType`，使用编译期可见的 ViewModel/命令类型，禁止通过反射绑定掩盖类型错误。视图映射和服务注册采用显式代码，配置序列化采用生成的类型元数据，不依赖运行时程序集扫描或动态 XAML。

先选择并锁定一个相互兼容的 Avalonia 12、LoreVcs、原生库和文本控件版本组合，记录包版本、上游提交（若必须使用源码）和测试服务器版本。使用集中包版本与锁文件使还原可重复。发布核对裁剪/AOT 诊断；不整体关闭分析或抑制第三方警告来获得表面通过。单个确有依据的抑制必须限定范围、解释原因并有发布运行用例。

采用目录发行包，包含主程序、`lorelib.dll`、渲染所需原生依赖、资源及许可文件；不以只有一个 exe 作为目标。测试以完整发行目录运行，普通调试构建通过不能替代 AOT 验证。

替代方案：JIT 发行不符合用户要求；直接沿用 SourceGit 的 Avalonia 11 依赖不符合版本约束。两者均不作为隐式降级路径。

### 2. 三个项目隔离 UI、应用逻辑与 Lore 实现

建议结构：

```text
src/SourceLore.App
  Views / ViewModels / Composition
             |
             v
src/SourceLore.Core
  Sessions / Operations / Domain models / Backend contracts
             ^
             |
src/SourceLore.Infrastructure.Lore
  LoreVcs adapter / Watcher / Local preferences / External tools

tests/SourceLore.Core.Tests
tests/SourceLore.Lore.IntegrationTests
tests/SourceLore.App.SmokeTests
```

Core 不引用 Avalonia 或 LoreVcs，拥有工作目录会话、版本/分支身份、变更快照、差异文档和操作结果类型。后端契约按工作流划分，避免一个通用字符串命令执行器。App 在启动组合这些实现；Infrastructure 映射具体 SDK 类型、认证和文件监控事件。

SourceGit 用作布局和交互参考。任何局部源码复用先检查 Avalonia 12 兼容性及依赖，保留来源和许可；首版无需把上游整体作为子模块。

替代方案：在 ViewModel 内直接调用 SDK 起步较快，但会把原生回调、版本差异与界面状态耦合。当前分层增加少量适配代码，换取可测试的错误和并发处理。

### 3. Lore SDK 是唯一仓库操作后端

使用 LoreVcs 的公开强类型 API，随应用携带匹配的 `win-x64` 运行包。启动先读取版本并验证已知支持组合；失败时提供明确诊断。SDK、原生库和测试服务器作为一组验证，不承诺兼容任意 pre-1.0 版本，也不承诺接入 UEFN 托管环境。

应用级管理原生运行库生命周期，不在关闭一个仓库标签时关闭全局运行库。参数、委托、句柄保持到操作真正结束。回调内把要跨线程使用的数据复制为自有托管模型，释放规则跟随当前 SDK 的文档和模板；不把借用的 FFI 事件存进 ViewModel。通过受控缓冲将进度合并后派发到 UI 线程，完成/失败事件不得被合并丢失。同步等待仅限后台执行，不阻塞 UI。

P/Invoke 本身可用于 NativeAOT，但这不能证明 LoreVcs 的所有路径已经兼容。第一个里程碑必须验证加载、状态、文本读取、暂存、提交、回调、错误及退出释放。发现 SDK 兼容问题时，在保持公开 Lore API 语义的前提下进行最小、可测试的绑定兼容修正，并记录补丁来源；不能通过改用 CLI 或 JIT 宣称满足要求。若硬约束仍无法满足，停止依赖该验证的实现并报告具体失败。

替代方案：解析 CLI 输出会引入进程、转义、输出格式和部署依赖；重写底层 Lore 实现会扩张维护边界，均不采用。

### 4. 用会话身份、操作互斥和状态代次管理并发

会话按后端解析的工作目录实例身份及规范根路径归属，不按远端 URL 合并；Windows 路径别名、大小写与同一路径重复打开需要去重。相同远端的不同工作目录使用独立 UI 状态。

每个工作目录有一个操作调度器。任何可能改变文件、分支、暂存或本地元数据的调用都经过串行通道，包括扫描和 dirty 更新；只有经版本验证可安全并发的只读查询才旁路执行。多实例共享存储时，保留 Lore 自身的锁/竞争检查；应用内部互斥不冒充跨进程事务锁。

查询携带会话身份、状态代次和选择代次。工作目录/分支/文件选择变化后，迟到结果被丢弃。取消查询只表示 UI 不再接受结果，除非已证实 SDK 能安全取消，否则仍保持资源到原生操作结束。写操作不提供未经验证的硬取消按钮；关闭窗口时等待其结束或明确提示仍在执行。

```text
Idle --> Running --> Reconciling --> Idle
            |              |
            v              v
        Conflicted      NeedsRefresh
            |
            v
     Resolving / Aborting --> Reconciling
```

记录最小未完成操作标记（实例、操作类型、起始版本、时间），不记录令牌和文件内容。重启、异常或完成结果不明确时，从后端重建真实状态；标记仅用于触发核对，不用于自动重放命令或恢复文件。

替代方案：仅禁用按钮不能阻止快捷键、后台扫描与重复请求竞争；乐观地更新当前分支/推送状态可能误导用户，因此以实际结果核对为准。

### 5. 文件监控提供增量线索，扫描负责恢复准确性

打开目录时执行一次扫描核对，随后对监控事件去抖、合并路径，并通过后端的 dirty/状态接口更新。事件溢出、重新获得焦点发现可能过期或用户刷新时执行重新扫描；忽略规则、文件状态和有效路径由 Lore 决定。

操作期间积累文件事件，完成后集中核对，避免客户端写入造成刷新风暴。长扫描显示状态可能过期；遇到拒绝访问或部分失败不得显示为干净。工作区模型同时保存 dirty 与 staged 状态，不从列表勾选自行推断仓库状态。成功暂存后重新读取实际状态；提交前核对选择和预览是否过期，允许用户继续编辑已暂存文件，并明确提交读取最新内容。

替代方案：每次刷新都全盘扫描实现简单但不适合大代码库；只依赖 watcher 会漏事件。因此采用增量更新加可恢复扫描。

### 6. 差异采用有界的文档模型与只读渲染

优先使用兼容 Avalonia 12 的官方 AvaloniaEdit 构建只读视图；第一里程碑验证 AOT、中文、行号、选择复制和滚动。若控件依赖不能满足 AOT，替换为自有虚拟化只读行视图，保持同一差异文档契约和全部展示模式；不引入 WebView 作为临时绕行，也不把复杂编辑器能力带入首版。

差异语义优先使用固定 Lore 版本提供的文本差异结果；适配层统一为行/hunk 模型，并保留两侧版本、路径、编码、换行和末尾换行信息。若后端对受支持的 UTF-16 内容不直接提供文本 diff，取得原始两侧内容后使用纯托管行比较补足展示，且通过相同 fixtures 校验。UI 渲染与差异计算分离，两种视图共享结果。

初始预览上限采用每侧 8 MiB、100,000 行、单行 100,000 字符；任一超限显示外部打开入口。这是集中可调整的预览策略，不是仓库存储限制。读取和计算均有界，不能先无界加载再判断超限。BOM 优先，支持 UTF-8 与带 BOM 的 UTF-16；无 BOM 内容用严格 UTF-8 解码，失败则不猜编码。预览不写回文件。

历史内容使用只读临时文件供外部工具打开，文件生命周期由客户端管理；以进程参数列表传递路径，不拼接 shell 命令。外部工具不可用时保留明确错误。初版不依赖语法高亮扩展才能完成差异验收。

### 7. 历史使用固定起点分页，分支切换先核对再更新

历史首次加载固定当前分支的起始版本，每页初始 100 条，通过后端枚举/游标推进；发现新版本时提示刷新并重建分页。合并版本保留全部父身份，默认比较后端主父版本，用户可选择另一父版本或指定两个历史版本。尚未缓存的历史内容允许失败并提示联网，不能用空数据掩盖。

未推送状态来自实际本地历史和最近一次成功核实的远端锚点，记录核实时间；查询失败时降级为过期/未知。不得借用 Git 的 ahead/behind 字符串解释 Lore 的状态。

首版创建分支仅从当前版本开始，并按 Lore 0.10.0 的原生语义立即切换到新分支。用户于 2026-10-13 确认采用这一范围：入口标为“创建并切换”，显示当前起始版本，成功后从后端核对当前分支与版本。历史版本创建和仅创建不切换留待后续扩展，不为此维护原生 API 扩展。

创建并切换与切换已有分支都核对本地变更和未完成操作。切换使用后端可用的预检和保留本地修改模式；dirty/staged 选择若不能保证保留，就拒绝切换并要求先处理，不增加首版强制重置入口。失败或结果不确定时重新读取实际状态，不根据请求名称乐观更新。操作后统一刷新实际分支、版本、变更和历史。

替代方案：一次性加载完整历史和根据名称自行模拟分支操作，都难以保证规模和语义正确性。

### 8. 认证与同步形成显式可恢复流程

提供 Lore SDK 认证入口，按 SDK 事件显示/打开登录 URL；认证会话及凭据持久化由 Lore 支持机制负责。客户端偏好文件只保存根路径、窗口布局、差异模式和非敏感设置。所有日志、异常映射及操作标记统一脱敏；不把 URL 内含的敏感参数原样写入记录。

推送与同步分开，默认不启用会隐式生成额外合并行为的可选推送优化。先核对本地状态，再调用当前版本对应的同步/合并操作。具体事件、返回码、继续和中止步骤必须以固定 SDK 与真实双工作目录用例验证，不能把 `sync` 简化为 Git pull 的包装。

冲突页展示文件和后端解决状态，提供外部编辑入口；返回后由用户显式标记解决并让后端核实。继续按钮仅在后端允许时启用。如果继续需要生成合并提交，先展示并确认合并说明；普通提交入口不能绕过该流程。中止先说明当前版本实测的数据影响并确认，不私自复制/覆盖整个工作树来模拟回滚。

网络错误和连接中断不自动重试写操作。先核对本地版本和可获得的远端状态，用户再明确重试。原生库自身可恢复传输的能力由它负责，不另造文件传输协议。

替代方案：仅显示错误弹窗然后把 CLI 留给用户，无法完成首版的同步闭环；内置三方编辑器则超出首版范围。

## Risks / Trade-offs

- [LoreVcs、原生回调或文本控件 AOT 未经实测] → 先完成发布产物中的最小真实链路，失败时修正绑定/替换渲染器；没有通过前不宣称兼容或扩展完整工作流。
- [Lore pre-1.0 API 和服务器行为变化] → 固定版本矩阵，以实际 SDK 能力记录和集成 fixtures 为准，升级单独验证，不自动更新运行库。
- [watcher 丢事件、扫描修改元数据] → 串行化元数据写操作，保留过期标记和重新扫描入口。
- [原生回调失效内存、界面线程访问和资源提前释放] → 回调内复制数据、完成事件后释放、发布构建覆盖重复操作与关闭场景。
- [外部 CLI 并发、网络中断造成结果不确定] → 后端核对和显式重试；应用互斥只保证本进程，不宣称排除所有外部竞争。
- [差异与历史内容过大] → 有界读取、分页、取消过期结果和明确退化；代价是大文件需要外部工具。
- [首版包含基础远端接入但不承担服务器管理] → 集成测试使用可重复的受控服务器，发行说明提供连接与兼容要求。

## Migration Plan

这是新应用，无旧数据迁移。实施按以下顺序交付：

1. 建立解决方案、依赖锁定与 Windows AOT 发布路径；固定 SDK/原生库/服务器组合，并验证必须的 API 与操作语义。
2. 在临时仓库完成打开、扫描、文本差异、文件暂存和提交的 AOT 真实链路，验证资源、回调与错误路径。
3. 补齐工作目录会话、认证、远端同步与冲突恢复，再完成历史和基础分支，并以全部规格场景验收。
4. 在未安装 .NET、Git 和 Lore CLI 的干净 Windows x64 环境运行完整目录发行包，核对中文/含空格路径、发布依赖、脱敏日志和双工作目录并发用例。

发行包携带自身原生库。回退应用时使用先前已验证的完整版本组合；不对用户仓库执行降级、重置或自动存储格式转换。发现数据格式或服务协议不能被旧版本支持时，停止并解释兼容性限制，而不冒险写入。

所有实际验证结果、依赖版本和必要的局部兼容补丁在实施阶段记录；本规划阶段没有执行编译、发布或修改用户 Lore 仓库。
